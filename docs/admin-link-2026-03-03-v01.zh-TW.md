# GET /admin/links API 規格

## 摘要

`GET /admin/links` 應被定位為管理後台的列表 API，不是統計 API，也不是單筆連結詳情 API。

它的主要目的如下：

- 讓管理者快速查找連結
- 讓管理者快速判斷連結狀態
- 支援篩選、排序與分頁
- 回傳適合列表顯示的輕量聚合欄位

這支 API 不應直接對 `link_click_events` 做重型即時統計。

## API 責任範圍

這支 API 適合處理：

- 依短碼搜尋
- 依長網址或建立者 email 搜尋
- 檢查連結是否為啟用、過期、停用或已刪除
- 查看建立者是誰
- 查看基本流量摘要（`clickCount`、`lastClickedAt`）

這支 API 不適合處理：

- 趨勢圖
- 來源頁分析
- 國家分布
- 裝置分布
- 重型統計聚合

這些應在未來拆分成獨立的 admin stats API。

## 建議回傳欄位

`data` 陣列中的每筆資料建議包含：

- `id`
- `code`
- `shortUrl`
- `longUrl`
- `targetDomain`
- `status`
- `isActive`
- `createdAt`
- `updatedAt`
- `expireAt`
- `deletedAt`
- `clickCount`
- `lastClickedAt`
- `creatorUserId`
- `creatorEmail`

### 補充說明

- `shortUrl` 為計算欄位，可由服務網域加上 `code` 組成
- `targetDomain` 由 `longUrl` 推導而來
- `creatorEmail` 應透過 `users` 關聯查詢取得，不應直接存入 `links`
- `clickCount` 應直接使用 `links.click_count`，不要在列表查詢時即時計算 `link_click_events`

## Status 設計

若 `status` 只是營運上的衍生狀態，建議不要作為 `links` 實體欄位儲存。

建議於查詢層用以下規則動態推導：

- `deleted`
  當 `deleted_at IS NOT NULL`
- `disabled`
  當 `deleted_at IS NULL AND is_active = FALSE`
- `expired`
  當 `deleted_at IS NULL AND is_active = TRUE AND expire_at <= now()`
- `active`
  其餘情況

### 範例 SQL 邏輯

```sql
CASE
    WHEN l.deleted_at IS NOT NULL THEN 'deleted'
    WHEN l.is_active = FALSE THEN 'disabled'
    WHEN l.expire_at <= now() THEN 'expired'
    ELSE 'active'
END AS status
```

## 建議 Query Params

第一版最基本建議支援：

- `page`
- `limit`
- `sortBy`
- `sortOrder`
- `q`
- `status`

延伸建議篩選條件：

- `creatorUserId`
- `dateFrom`
- `dateTo`
- `domain`
- `hasClicks`

### Query Param 行為建議

- `q`
  建議搜尋欄位：
  - `code`
  - `long_url`
  - `users.email`
- `status`
  建議值：
  - `active`
  - `expired`
  - `disabled`
  - `deleted`
- `hasClicks`
  建議語意：
  - `true` => `click_count > 0`
  - `false` => `click_count = 0`

## 建議排序欄位

排序建議採白名單，不開放任意欄位。

建議支援的 `sortBy`：

- `created_at`
- `updated_at`
- `expire_at`
- `click_count`
- `last_clicked_at`

建議預設排序：

- `created_at DESC`

## 資料來源規則

`GET /admin/links` 建議的查詢來源如下：

- 主要來源：`links`
- 關聯來源：`users`（用來取得建立者資訊）
- 不要在列表查詢時即時聚合 `link_click_events`

### 欄位對應建議

- `clickCount` => `links.click_count`
- `lastClickedAt` => `links.last_clicked_at`
- `creatorEmail` => `users.email`
- `creatorUserId` => `links.creator_user_id`

## 效能考量

為了讓列表查詢維持快速：

- 使用 `links.click_count` 作為反正規化聚合欄位
- 使用 `links.last_clicked_at` 作為最近活動快取欄位
- 避免在列表查詢中對 `link_click_events` 做 `COUNT(*) GROUP BY`
- 保持這支 API 專注於列表用途

這樣可確保：

- 管理列表查詢維持快速
- 依 `clickCount` 排序成本低
- 分頁表現穩定
- 後續重型分析可拆到獨立 API

## 建議未來擴充的 API

為了保持 `GET /admin/links` 精簡，後續統計建議拆成：

- `GET /admin/links/:id`
  單筆連結詳情
- `GET /admin/links/:id/stats`
  單筆連結統計摘要
- `GET /admin/links/:id/stats/trend`
  單筆連結趨勢資料
- `GET /admin/links/top`
  排行相關 API
