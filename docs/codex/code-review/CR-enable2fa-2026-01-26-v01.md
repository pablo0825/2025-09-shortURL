## TL;DR（最重要 5 點）
1. `src/controller/user.controllers.ts` 的 `enable2fa` 交易區塊在 `userVersion.rowCount === 0` 直接 `return`，**未先 ROLLBACK**，可能留下未結束交易或讓連線處於 failed/idle-in-transaction。  
2. `enable2fa` 對 **錯誤的 TOTP** 沒有次數限制或鎖定機制，Redis key 仍保留，**可在 TTL 內暴力嘗試**。  
3. `enable2fa` 未檢查 **已啟用 2FA 的使用者**，允許重複啟用並重新產生 backup codes，可能被濫用。  
4. Redis 的 pending secret **解密與 DB 更新流程缺少結構化驗證與審計記錄**，維護與追蹤困難。  
5. `enable2fa` 混合了驗證、解密、DB 交易、備援碼生成與回應，**職責過多、可讀性低**，不利測試與維護。

## High risk issues（安全/資料風險，附影響與建議修法）

1. **2FA 驗證暴力嘗試風險**  
   - 位置：`src/controller/user.controllers.ts` → `enable2fa` → `verifyTotpCode` 後的錯誤回應區塊（`if (!isValid)`）  
   - 影響：`nonce` 在 TTL（10 分鐘）內可被無限制嘗試，若有人拿到 `nonce` 就可暴力嘗試 OTP。  
   - 建議：在 Redis 設定嘗試計數（例如 `2fa:attempts:${userId}:${nonce}`），超過門檻立即刪除 pending key 或鎖定；或驗證失敗就刪除 pending key 並要求重新 `setup2fa`。

2. **交易未 rollback 就 return**  
   - 位置：`src/controller/user.controllers.ts` → `enable2fa` → `userVersion.rowCount === 0` 的 `return res.status(404)...`  
   - 影響：交易已 `BEGIN`，未 `ROLLBACK` 即返回，可能造成連線留在 transaction 狀態，影響後續請求。  
   - 建議：所有 early return 前都先 `ROLLBACK`，或用集中式 `try/finally` 包裝，確保交易一定結束。

3. **允許重複啟用 2FA / 重新產生 backup codes**  
   - 位置：`src/controller/user.controllers.ts` → `enable2fa` → DB `SELECT twofa_backup_codes_version ... FOR UPDATE`  
   - 影響：若使用者已啟用 2FA，仍可用同流程重置 backup codes，不需再驗證密碼或現有 2FA，可能被盜用 session 濫用。  
   - 建議：新增檢查 `twofa_enabled`，若已啟用則拒絕或要求再輸入密碼/現有 2FA。

## Bugs / Logic issues（可能的 bug）

1. **未對 Redis 解析結果進行結構檢查**  
   - 位置：`src/controller/user.controllers.ts` → `enable2fa` → `const parsedData = JSON.parse(raw)`  
   - 問題：若 Redis 資料結構不符合預期（缺少 `encrypted` / `iv` / `authTag`），`Buffer.from(undefined)` 會 throw，但 error response 只回 500，排查困難。  
   - 建議：對 `parsedData` 做 shape 驗證（zod / 手動），並分支回 400 + 刪除壞資料。

2. **Redis key 刪除未處理失敗**  
   - 位置：`src/controller/user.controllers.ts` → `enable2fa` → `await redis.del(redisKey)`  
   - 問題：刪除失敗不會回報，可能留下可重複使用的 pending key。  
   - 建議：wrap try/catch 記錄 warning；必要時在成功啟用後強制刪除或設短 TTL。

3. **回傳 2FA backup codes 時未記錄 user_log**  
   - 位置：`src/controller/user.controllers.ts` → `enable2fa` → 成功回應區塊  
   - 問題：沒有對啟用 2FA 與備援碼產生寫入 audit log，降低可追溯性。  
   - 建議：呼叫 `writeUserLogToDB`，紀錄動作與 IP/User-Agent。

## Design / Architecture（架構與模組切分建議）

1. **單一函式責任過大**  
   - 位置：`src/controller/user.controllers.ts` → `enable2fa`  
   - 建議：拆分成 `loadPending2faSecret`、`verifyTotp`、`rotateBackupCodes`、`enable2faTx` 等小函式，方便測試與重用。

2. **2FA 流程邏輯分散在 controller**  
   - 位置：`src/controller/user.controllers.ts` → `setup2fa` / `enable2fa`  
   - 建議：抽出 `services/2fa.service.ts`，controller 僅負責 request/response；可提升維護性並集中處理安全策略（attempt limit、audit log 等）。

## Consistency / Style（命名、錯誤處理、logging、typing）

1. **錯誤訊息風格不一致**  
   - 位置：`src/controller/user.controllers.ts` → `enable2fa` 的多個 `res.status(...).json({ error: ... })`  
   - 問題：中英混用、訊息結尾不一致（有/無標點），不利前端統一處理。  
   - 建議：統一錯誤訊息模板與語系，集中在 error helper。

2. **缺少明確錯誤分類**  
   - 位置：`src/controller/user.controllers.ts` → `enable2fa`  
   - 問題：Redis / JSON parse / decrypt 都回 500，無法區分 user error vs system error。  
   - 建議：針對不可恢復資料（壞的 pending secret）回 400，並刪除 Redis key。

3. **命名一致性**  
   - 位置：`src/controller/user.controllers.ts` → `enable2fa` → `codeAndNonceParams`, `redisKey`, `raw`  
   - 建議：可更語意化，例如 `pending2faKey`, `pendingPayload`，降低閱讀成本。
