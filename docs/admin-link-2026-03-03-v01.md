# GET /admin/links API Spec

## Summary

`GET /admin/links` is designed as an admin list API, not a statistics API and not a single-link detail API.

Its primary goals are:

- Let admins quickly find links
- Let admins quickly judge link status
- Support filtering, sorting, and pagination
- Return lightweight aggregate fields suitable for list views

This endpoint should not perform heavy real-time analytics from `link_click_events`.

## API Responsibility

This endpoint is intended for:

- Searching by short code
- Searching by long URL or creator email
- Reviewing whether a link is active, expired, disabled, or deleted
- Seeing who created the link
- Viewing lightweight traffic summary (`clickCount`, `lastClickedAt`)

This endpoint is not intended for:

- Trend charts
- Referrer analysis
- Country distribution
- Device distribution
- Heavy statistical aggregation

Those should be handled by separate admin stats endpoints in the future.

## Recommended Response Fields

Each row in the `data` list should include:

- `id`
- `code`
- `shortUrl`
- `longUrl`
- `targetDomain`
- `status`
- `isActive`
- `createdAt`
- `updatedAt`
- `expireAt`
- `deletedAt`
- `clickCount`
- `lastClickedAt`
- `creatorUserId`
- `creatorEmail`

### Notes

- `shortUrl` is a computed value based on the service domain plus `code`
- `targetDomain` is derived from `longUrl`
- `creatorEmail` should be queried by joining `users`, not stored directly in `links`
- `clickCount` should come from `links.click_count`, not from counting `link_click_events` in real time

## Status Design

`status` should not be stored as a physical column in `links` if it only represents derived operational state.

It should be computed in the query layer using:

- `deleted`
  When `deleted_at IS NOT NULL`
- `disabled`
  When `deleted_at IS NULL AND is_active = FALSE`
- `expired`
  When `deleted_at IS NULL AND is_active = TRUE AND expire_at <= now()`
- `active`
  Otherwise

### Example SQL Logic

```sql
CASE
    WHEN l.deleted_at IS NOT NULL THEN 'deleted'
    WHEN l.is_active = FALSE THEN 'disabled'
    WHEN l.expire_at <= now() THEN 'expired'
    ELSE 'active'
END AS status
```

## Recommended Query Params

Minimum recommended query params:

- `page`
- `limit`
- `sortBy`
- `sortOrder`
- `q`
- `status`

Recommended extended filters:

- `creatorUserId`
- `dateFrom`
- `dateTo`
- `domain`
- `hasClicks`

### Query Param Behavior

- `q`
  Suggested search targets:
  - `code`
  - `long_url`
  - `users.email`
- `status`
  Allowed values:
  - `active`
  - `expired`
  - `disabled`
  - `deleted`
- `hasClicks`
  Suggested meaning:
  - `true` => `click_count > 0`
  - `false` => `click_count = 0`

## Recommended Sort Fields

Sorting should use a whitelist, not arbitrary columns.

Recommended supported values for `sortBy`:

- `created_at`
- `updated_at`
- `expire_at`
- `click_count`
- `last_clicked_at`

Recommended default sort:

- `created_at DESC`

## Data Source Rules

For `GET /admin/links`, the recommended data source is:

- Main source: `links`
- Join source: `users` (for creator info)
- Do not aggregate `link_click_events` in real time for list rendering

### Field Mapping

- `clickCount` => `links.click_count`
- `lastClickedAt` => `links.last_clicked_at`
- `creatorEmail` => `users.email`
- `creatorUserId` => `links.creator_user_id`

## Performance Considerations

To keep this list endpoint fast:

- Use `links.click_count` as a denormalized aggregate field
- Use `links.last_clicked_at` as a denormalized recent-activity field
- Avoid `COUNT(*) GROUP BY` over `link_click_events` inside the list query
- Keep the endpoint focused on list use cases only

This ensures that:

- Admin list queries remain fast
- Sorting by `clickCount` is cheap
- Pagination stays predictable
- Heavy analytics can be moved to dedicated endpoints later

## Recommended Future Endpoints

To keep `GET /admin/links` focused, future analytics should be split into separate endpoints:

- `GET /admin/links/:id`
  Single link detail
- `GET /admin/links/:id/stats`
  Single link stats summary
- `GET /admin/links/:id/stats/trend`
  Single link trend data
- `GET /admin/links/top`
  Ranking endpoints

## Suggested Implementation Structure

Following the current project layering:

- Route
  Define `/admin/links`
- Controller
  Validate admin identity and query params, call service, return JSON
- Service
  Handle list query orchestration and response shaping
- Repository
  Contain SQL for list query and count query

Suggested file layout:

- `src/controllers/admin-controllers.ts`
- `src/services/admin/admin-link-service.ts`
- `src/repositories/admin/link-repository.ts`
- `src/schemas/admin-schema.ts`
